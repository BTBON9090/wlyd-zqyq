# 前端开发计划与业务重构

## 目标与依据

依据工作区原型源代码：原 `App.tsx` 的模块路由，`Home.tsx` 的服务矩阵，`LoginForm.tsx` / `AuthContext.tsx` 的短信与密码流程，`onboarding` 的三种企业关联方式，`enterpriseServices.ts` 的 11 类 14 项服务，以及 `ServiceDetailPage.tsx` / `ServiceOrderPage.tsx` 的详情与需求步骤。

资料中没有独立需求说明、已批准视觉稿、真实 API 文档或正式部署账号。本轮以前端原型为业务依据，以用户指定的三部分为交付范围。

## 原型审阅结论

| 原问题                                       | 用户受到的影响           | 本轮处理                                 |
| -------------------------------------------- | ------------------------ | ---------------------------------------- |
| 首页同时展示补贴、地图、金融、行情、AI、交易 | 用户难以识别当前能办的事 | 先突出服务搜索、类别和清晰的办理路径     |
| 未登录点详情触发登录拦截                     | 尚未看清价值即要求注册   | 列表与详情公开，在提交申请时登录         |
| 注册即强制进入复杂入驻                       | 咨询用户被资质流程阻断   | 账号与企业认证分开，允许稍后办理         |
| 无后端却宣称真实企信数据、补贴和指标         | 容易形成错误预期         | 去除没有依据的背书与精确指标             |
| 「去支付」只显示演示 Toast                   | 无可追溯的真实业务结果   | 改为服务申请，提供申请编号与记录         |
| 人脸和电子签章为前端演示                     | 容易误以为身份核验已完成 | 不提供假核验；留待真实身份服务接入       |
| 文字偏内部术语（级联类目、节点管控等）       | 理解成本高               | 改为服务名称、范围、费用、步骤等用户语言 |
| 多文件重复覆盖 CSS                           | 后续主题修改易发生偏差   | 四层样式、统一语义 token 和共享组件      |
| 固定验证码、明文密码及模拟 SSO 混在业务代码  | 演示逻辑可能误入正式发布 | 开发适配器独立，生产编译排除             |

原品牌处理：保留「万」标识与集团技术支持语义，延续蓝色方向；去掉 `xx` 占位在客户主界面的重复出现，用可配置名称替代。原字体依赖 Google Fonts，改为本地系统中文字族，不依赖境外字体网络。

## 尚待业务确认的事项

- 企业审核中是否可「咨询」还是可直接「下单」：本期仅允许提交无付款的咨询申请。
- 企业创建、已有成员加入是否需要不同资料／协议：当前按最小资料收集，不赋予自行选角色的能力。
- 正式交易要支持哪类计费与分期：本轮保留原型参考价格，未开发支付与合同。
- 多园区、多企业账号切换的优先级：本轮围绕一个部署园区和一个活动企业身份验证风格。
- 真实短信异常码、发送限流和验证码有效期需由后端最终决定。

这些问题不阻断当前视觉与流程试点，但应在交易型能力开发前确认，避免后续返工。

## 第二版首页方向修订

客户最新要求优先于此前流程简化判断。V2 已恢复平台宣传首页定位，纳入原型六大业务、服务券展示、产业资源与生态合作，并补充紧凑服务陈列。Banner 与服务封面必须保留运营/商家图片位。详见 [第二版首页](HOMEPAGE_V2.md)。

后续企业服务应优先对齐 `客户端/src/data/publishedServices.ts` 的发布模型：服务封面与相册、店铺资料、三级分类、规格价格、一次性/分期付款、验收、案例和评价。这些是有效业务需求，不能把当前需求申请的临时实现当作最终交易方案。下一轮应先核对列表/详情/供应商发布字段的一致性，再推进交易流程；首页本轮不扩展其他业务页面。
